# EMARX 审计—修复两阶段协议

本协议适用于对已有稿件的修改任务：用户草稿、旧版交付稿、外审退回稿、要求"再仔细检查一遍"的成稿。从零写作仍按 `production-workflow-v7.md` 执行。

核心原则：**先把问题查清楚、列成清单，再按清单逐项修复。不边查边改，不凭印象改。**

## 一、阶段一：只读审计

1. 不改动任何正文、脚注、参考文献和交付文件。本轮唯一产物是问题清单。
2. 不沿用稿件自带的"已审定稿"结论，把已交付稿当作待审稿件重新审。
3. 多条线并行扫描，至少覆盖：
   - 引注与文献（脚注规范、GB/T 7714、复合脚注、重复著录）；
   - 经典原句（篇名—卷次—页码一致性、版本错配、脚注边界污染）；
   - 概念边界（前后定义矛盾、概念层级混用）；
   - 论证逻辑（因果跳跃、后见之明、无证据推断）；
   - 主题集中度（章节偏离核心对象的比例和位置）；
   - 学科范式（是否符合马克思主义理论等学科的论证方式）；
   - 元话语与成文风格（自我叙述、导游句、模板句式）；
   - 章节结构（标题递进、内容重复、层级深度）。
4. **量化输出**。元话语、设问导语、破折号、对称结构等给出出现次数和章节行号，不写"较多""存在一定问题"这类模糊词。
5. 每条问题记录：严重度 / 位置（章节、行号或可检索的原文片段）/ 证据 / 修改方向 / 验证方式。
6. 清单保存到运行目录（如 `03_审校记录/问题清单_<日期>.md`），向用户汇报清单要点后，再进入阶段二。

## 二、阶段二：按清单逐项修复

1. 顺序：先修硬伤（引文错配、缺页码、格式错误），再重构论证（概念边界、主题漂移、因果链），最后统一格式和文风。
2. 每修完一类问题立即验证（脚本对账 + 人工回读），不带着失败进入下一类。
3. 修复过程中发现清单之外的问题，补录进清单，不悄悄带过。
4. 禁止防御性写作：不用"本文需要谨慎""不能简单地说"遮蔽论证空缺，论证空缺就补论证或删判断。

## 三、回归审计

1. 修复完成后，用阶段一的同款检查重新扫描，确认问题清零。
2. 残留问题必须列入交付报告的残余风险，不得因为"改过了"就默认消失。

## 四、版本回退与作废声明

大规模改写（重排脚注、批量合并、整章重写、全局替换）必须遵守：

1. **改写前建立基线备份**：复制源稿到带时间戳的备份目录（如 `_backup/<时间戳>/`）。
2. **发现处理过度时立即回退**：典型信号——误删了不同原句的独立出处、误合并了不同页码的引用、为减字数删掉有效论据、替换破坏了理论关系词。回退到基线，重新按更小粒度处理。
3. **作废声明**：被回退的中间版本必须明确声明作废（"X 条脚注版本作废"），其统计数字不得写进交付报告。交付报告只反映最终版本的实测数字。
4. 回退不是失败，是正常工序；但同一类过度处理反复出现，说明方案粒度过大，应缩小处理单元。

## 五、证据纪律

1. 审计结论必须有行号或可检索原文作证据。
2. 复核发现原审计结论错误时，明确撤回（写明"原清单把 X 列为问题是不准确的，实际……"），不掩盖旧结论。
3. 无法核验的页码、出处不补造，列入残余风险。
4. 交付报告中的每个数字（脚注数、参考文献数、字数、页数）都必须来自最终文件的实际测量，不引用中间版本数字。
